1. 设计目标与系统边界

系统关注的是“市场信号”而不是普通聊天摘要：谁在供给/需求什么资源、价格和数量是什么、信息是否当前有效、是否已经形成交易承诺，以及每个结论由哪些原始消息支持。

可审计每个 signal 保留 source message IDs、用户、群组、原始价格/数量和解释。
可回放原始 JSONL append-only；模型或 prompt 改变后可以重新跑同一批数据。
不确定性优先缺失单位、币种或资源时保留 unknown，不伪造精确值。
模型可替换OpenRouter 只通过 provider adapter 接入，主模型和 fallback 可配置。

3. 数据结构

字段含义

AggregatedTrend · Dashboard 聚合行

每一行对应一个规范化资源，分别统计 supply/demand volume、signal 数、median/P25/P75、sample count、independent offers、平均置信度和 availability。没有足够数据的字段在 UI 中显示为空白。

4. Context 如何切分

Context 是理解一组市场信号所需的 conversation unit，不是单用户 unit。一个 context 可以包含多个用户，也可以生成多个 resource-level signals。

优先级规则例子
1 · Reply thread从 root 出发收集完整 reply tree；reply chain 优先于时间窗口。Need → I have → Deal = 1 context
2 · Group window没有 usable reply 时按 group_id 和 inactivity window 合并。默认 120 秒，同群相近消息可合并
3 · No author-only merge不能只因为同一用户或时间接近就合并无关话题。Claude 和 A100 可能仍是不同语义
4 · Multi-resource一个 conversational context 可以包含多个资源；拆分在 normalization/aggregation 阶段完成。一条 bundle offer 产生多个 signals
5 · Size guardrails生产环境增加 max messages、max tokens、max thread duration。超限在安全边界切分并保留 provenance
评估指标要分开看：Chats tested 是原始消息行数；Contexts sent 是组装后发送给模型的批次数；二者不是同一个数量。

4.1 Combined message window 的准确率/效率平衡

窗口变大并不一定让效果更好。更长的窗口能提供更多上下文，减少省略实体和代词造成的误判，但也会把无关话题、不同资源和不同交易混进同一个 prompt，增加 token 成本、延迟和 false association。

窗口可能收益主要风险适用情况
短，例如 30-60sprompt 小、延迟低、话题纯度高。容易拆散 follow-up、correction 和慢回复。高频群、话题切换快、消息带明确实体。
中，例如 120-300s通常能覆盖短交易对话和补充说明。活跃群中可能混入第二个话题。当前 prototype 的默认起点。
长，例如 600s+有利于低频群、延迟回复和较长谈判。token/费用上升，模型更容易错误关联不同报价。低频、主题集中的群，且应配合 topic/token guardrail。
效果指标signal precision/recall、entity inheritance、correction accuracy、false merge rate、false split rate、transaction-state accuracy。
效率指标contexts 数、平均 chats/context、input tokens、P50/P95 latency、API cost、fallback rate、parse failure rate。
业务指标重复 offer 数、错误价格关联、错误成交状态、snapshot 稳定性，以及分析人员需要人工修正的次数。

4.2 如何找到合理窗口

应使用更真实、带 conversation/thread label 的消息样本做 window sweep，而不是凭感觉选一个数字。推荐固定模型、prompt 和 normalization 版本，对多个候选窗口重复跑同一数据：

candidate_windows = [30, 60, 120, 300, 600]

for window in candidate_windows:
    contexts = assemble_contexts(messages, inactivity_seconds=window)
    evaluate(
        context_precision,
        context_recall,
        signal_field_accuracy,
        false_merge_rate,
        false_split_rate,
        input_tokens,
        latency,
        api_cost,
    )

选择 Pareto frontier，而不是只追求单一准确率：如果 300 秒只比 120 秒多 0.5% field accuracy，却增加 40% tokens 和 25% false merge，120 秒更合理。不同 group 可以采用不同窗口，例如高频交易群 60 秒、低频资源群 300 秒。

重要：明确的 reply_to 不应受 inactivity window 限制。窗口只处理没有 reply metadata 的消息；reply tree 始终优先。

5. 特殊 scenario 处理

Scenario处理策略Golden 验证点
Correction后续 correction 覆盖旧值；SQLite 根据 source IDs 删除/替换旧 signal。最终价格保留，旧价格不进入 snapshot。
Demand bound保留 raw phrase，并将 below 4 归类为 upper_bound。request + demand + price_type。
Bundle offer同一 context 允许返回多个 resource signals。AWS/GCP 都被识别。
Historical标记 historical/hearsay，不混入当前可比报价。temporal_status。
Commitmentreply chain 继承资源；明确 “Deal, PM me” 视为 commitment，不等于 completed。resource 与 transaction_status 可由 context 中不同 signals 共同满足。
Availability没有明确价格也可以生成 availability signal；不虚构库存量。constrained / unavailable。
Irrelevant无市场动作的事实或闲聊应 abstain。no_actionable_signal。

6. UI 报告字段解释

Dashboard · Market snapshot

列含义
Resource规范化资源名，例如 OpenAI Credits、A100 GPU。
Supply volume / Demand volume分别汇总供给和需求数量；单位不兼容时不强行相加。
Median price / P25 / P75在币种、单位、price semantics 可比时计算；缺数据为空白。
Samples参与该资源聚合的信号数。
Independent offers按 offer/source 独立性去重后的供给数量。
Confidence信号 confidence 的平均值，不代表统计置信区间。
Availabilityavailable、unavailable、constrained 或 unknown。

Extracted signals

逐条显示 LLM 输出经过 provenance 和 normalization 后的结果。Evidence 是支持该结论的消息 ID；Explanation 是短解释；没有价格或数量时显示空白。
